# Incremental indexing execution ledger

Purpose: the single checked-in record of execution state for the incremental indexing and worktree
write-amplification work on branch `fix/incremental-index-write-amplification`. It carries one row
per work item (W1–W9 and the F fix series), the ten acceptance gates with their final state, the
declared limitations, the coordinator decisions with their evidence-based corrections, the
measurement summary, and a compressed evidence log — one line per wave.

The [design and implementation history](incremental-indexing-write-amplification.md) records
invariants and the chronological component narrative; the [paired
measurements](incremental-indexing-measurements.md) are the only place a performance claim about
this branch may be made. This ledger records *what is done, proven, or open right now*. It does not
restate either of the other two.

This revision consolidates the previous append-only wave log. Every wave's own exit entry is
compressed into the Evidence log appendix; the per-item facts it carried are folded into the item
rows. Nothing is deleted that a reader needs to audit a claim: every row names the result
directories and the lane reports its counts came from.

## State vocabulary

These eight states are used verbatim and exclusively. No other status word appears in this ledger.

| State | Meaning |
| --- | --- |
| `proposed` | Described and scoped; no source written for it yet. |
| `implemented` | Source exists on disk (committed or dirty). **Never implies production activation.** |
| `compiled` | The owning package builds from actual source after the last relevant edit. |
| `tested` | Named regressions ran and passed against that compiled source, with counts recorded. |
| `wired` | A production entrypoint actually reaches the code on a default path (no private overlay, no test-only caller). |
| `E2E validated` | Proven through an isolated public-path end-to-end run **at the final source identity**, not a unit fixture and not an earlier candidate. |
| `complete` | `wired` + `E2E validated` + its acceptance gate closed with durable recorded evidence. |
| `blocked with evidence` | Cannot progress; the blocking failure is named with file, test, and observed output. |

`implemented` never implies production activation. A component that exists and passes tests but is
not reachable from a default startup, watcher, or Git callback path is `implemented`, never `wired`
and never `complete`.

**No item in this ledger is `complete` on the strength of an end-to-end run at the final HEAD.** The
E2E matrices (W8.5, W8.7, W8.8, W8.10) and the paired measurement (W8.4, F6) that the item rows cite
were driven against earlier candidate binaries — `gortex-2fd5db82`, `gortex-271a9e9f` — which are
ancestors of the final source, not that source itself. The Final-source validation row in the
evidence log re-ran all seven matrices at `9fc2e7ce`: **4 PASS (4, 5, 6, 7), 3 FAIL (1, 2, 3)**,
every red reproducing byte-identically on `gortex-271a9e9f`, so it confirms the item rows rather
than closing a gate. Where an item row says `complete`, that word is used in its
narrower per-item sense recorded by the wave that landed it (implemented + compiled + tested +
wired + verifier `pass`); it is **not** a gate closure. The gate table below is the authority on
what is closed, and it closes nothing.

  `HOME` and `XDG_{CONFIG,DATA,CACHE,STATE}_HOME` / `XDG_RUNTIME_DIR` per run under
  `harness/home-<run-id>/`. Git isolated (`GIT_CONFIG_GLOBAL`/`_SYSTEM=/dev/null`,

  failures that were harness artifacts, not code

- **CWD** is the package source directory, so source-auditing tests such as
  `TestGenerationCapabilityChecklistIsComplete` see their own package.
- **Daemon unreachability.** `GORTEX_AUTOSTART=0` plus
  `GORTEX_DAEMON_SOCKET/PIDFILE/STATEFILE/LOGFILE/SNAPSHOT` pinned into the short private root. The
  user's live daemon socket is unreachable from any harness run.
- **Run knobs.** `GOMAXPROCS=2`, `GOMEMLIMIT=2GiB`, **`-test.timeout 8m` hardcoded**

### The W4.8 two-regime contract (W4.7's correction, recorded because it is easy to get wrong)

A dependent's behaviour after a committed base advance depends on whether the family's primary has a
published generation:

- **Published-generation regime** (`checkout_coordinator.go:1654-1675`): the dependent's routed pair
  `B1 + D1` is **not stale** after the advance. `MaterializeCheckout` walks the routed generation's
  own immutable `BaseGenerationID` chain (`graphview/materialize.go:321-323`, `:404`, `:520-539`)
  and never reads the family's active pointer. Recomposition therefore buys **currency and
  availability, not correctness** — and the pin (W4.8) is what buys the saving.
- **No-published-generation regime** (`:1679-1687`, `primaryBase.generationID == 0`): the delta names
  no ancestor (`generationAncestry`'s `generationID > 0` loop terminates at zero) and composes over
  the shared corpus, which is rewritten in place. Here **recomposition is the correctness
  requirement** and a regime-blind pin would be a correctness bug.

W4.7's source comment says this in as many words, including "do not read this path as 'W4.8 is
done'". W4.8's pin is refused four independent ways in the legacy (generation-0) regime.

### Two contracts that must not be weakened

- **`require_exact` refuses drift.** `require_exact` is keyed on `!outcome.fresh`, not on a reason
  whitelist, so a newly added `fresh_reason` cannot bypass it (W5.9). W5.7b withdraws exactness as
  soon as a route-epoch mismatch is confirmed, above the per-capability dedupe, so one lane's
  annotation cannot leave another lane's answer `exact:true`. W5.7c refuses a withdrawn-exact view
  **before an effectful tool runs**, read-only by construction. Every fallback stays read-only.
- **Tool lists never grow.** The `tools/list` byte ceiling is a hard gate and it bit during W3.2
  (the shipped `profile` arg wording is **+1 byte**, so the multi-repo rule had to live in the
  unserialized doc comment and the refusal text). W5.9 gained its head-room by **shortening the
  profile bodies** rather than raising the ceiling — core 4605 → 4360 against an unchanged 4608
  (5.38 % head-room), localization 3677 → 3552 (7.50 %), full 7518 → 7356 (10.21 %) — and
  `TestProfileBodiesKeepCeilingHeadroom` reads `bodyByteCeilings` instead of restating it, so
  **raising a ceiling raises the bar**.

### D8 — the upgrade cost, stated for the PR

> W2.1c and W2.4 each invalidate every cached generation **once** on first contact with this binary:
> the widened `config_hash` (now over the frozen configuration snapshot's versioned fingerprint plus
> six named domain digests, where it was `indexConfigHash` over the index configuration alone) and
> the newly non-empty `dependency_revision` each re-key every stored checkout generation, so every
> layer rebuilds once. The two are bundled into one deliberate deploy. Separately, the store takes an
> **additive migration to schema v25** (W3.3: a `view_gen` column on `analysis_generations`, with
> `analysis_active_generation` re-keyed on `(view_gen, slot)`); legacy rows are copied at
> `view_gen 0` and generation zero is not relabelled, and the newer-schema refusal still works. There
> is **no** down-migration: W6.1's `ownership_mode='context'` is a vocabulary extension in a plain
> TEXT column with no version gate, so a binary predating this branch reads such a row as a claim
> with no payload and serves that path empty until the generation is rebuilt. Plan for one full
> re-index per tracked checkout on the first start after the upgrade, and do not roll the binary back
> across a store that has published a context-mode generation.

### What was NOT measured — stated honestly

- **SSD wear.** `ri_logical_writes` counts bytes a process asked the kernel to write. Write-back
  coalescing, the filesystem's bookkeeping and the drive's FTL all sit between that number and NAND.
  **Process writes are not NAND writes.**
- **Cumulative writes from file sizes.** **A WAL size is not cumulative writes.** WAL sizes appear
  as *state at a phase boundary*, next to the write series, never instead of it.
- **Checkpoint counts.** `wal_resets` is a **lower bound** — a PASSIVE checkpoint that does not
  restart the log is invisible from outside the process.
- **Sustained production behaviour.** 1,500 generated Go files over ~10 minutes per arm-repetition,
  with an accelerated janitor, is a controlled comparison between two binaries, **not** a forecast of
  a week on a real repository.
- **Default configuration.** `GORTEX_RECONCILE_INTERVAL=5s` accelerates the janitor from a 1 h
  default in every measured arm; §4 of the measurements document lists every other differing knob.
- **The 6,000-file scale axis, post-fix.** Never re-run. `P1@6000` 7.44× and `P4@6000` 674× have no
  post-fix counterpart, and the 6,000-file candidate `P5` arm **did not finish** — it failed its
  trailing single-shot isolation probe after all 20 commits and 230 exactness waits succeeded, with
  the diagnostics showing all ten dependents `composed`/`route.ready`/`exact:true` a moment later.
  **Whether the dependent view leaked is unanswered, not answered in the negative.** The guard was
  not relaxed to make the arm finish.
- **A fresh baseline arm for the second verdict.** By design — re-freezing would make the two
  verdicts incomparable — but the ratios therefore carry uncontrolled host drift that the original
  interleave shared between the arms. The order-of-magnitude movements are outside that drift;
  `P6` 1.05→0.76 and `P3` 0.89→0.92 are not.
- **The mechanism behind `P4`'s surviving 1.28×** (112,432 median bytes). The counters say what it is
  *not*: no publication (6 dispatched, 6 skipped), no generation movement, not the amend alone.
- **A partition of checkpoint versus non-checkpoint work.** The checkpoint-excluded series is an
  **upper bound** on non-checkpoint work; attribution is per 1 Hz sample interval.
- **Anything but darwin/arm64**, at n = 3, medians with min/max, no confidence intervals, with the
  host's load uncontrolled. A few per cent is noise.
- **F2's second-copy payload ceiling and F4's daemon-level 60 s idle window** — neither was run.
  **F3b's single-phase re-measurement was run and missed both of its targets.**
